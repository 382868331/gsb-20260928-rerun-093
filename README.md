# 消息投递运行系统（第二阶段）

本地持久化消息投递：主题、订阅、消费位置、独占投递与确认，以及延迟投递、失败退避、隔离与人工重新投递、全量消息历史。生产与消费均由项目内测试端（broker/ 下 *_test.go）完成，不接中间件。路由能力留待后续阶段。

## 结构

- broker/broker.go — 主题/订阅/消费位置、Pull/Ack、超时回收与纪元 fencing
- broker/store.go — 磁盘持久化与重启恢复
- broker/broker_test.go — 测试端（生产者 + 多消费者场景）

## 持久化布局

- topics/<topic>.jsonl — 消息日志（追加写 + fsync）
- subs.json — 订阅、已确认偏移、失败计数、退避截止、隔离/放弃集合与每条消息累计尝试数（临时文件 + rename 原子重写）
- acks.jsonl — 每条消息的实际去向记录（谁、何时、以何纪元确认）
- history.jsonl — 消息历史：每一次领取、超时、拒绝、确认、隔离、人工重投、人工放弃各一条（追加写 + fsync）

## 语义

- 每条消息同一时刻只有一个当前持有人（可见期内其他消费者拉不到）。
- 超时未确认即回收转交，纪元递增；旧持有人的 Token 立即失效（ErrStaleToken），不会误伤新持有人。
- 确认写盘后才算完成；普通重启后已确认消息不会重来，未确认消息允许重新投递。
- PublishDelayed 延迟投递：到期前对消费者不可见。
- Nack 拒绝投递：进入退避（backoffBase * 2^(n-1)，SetRetryPolicy 可调），退避结束自动重新投递，Attempt 递增。
- 失败次数达上限的消息被隔离：不再自动投递，也不阻塞同订阅后续可处理消息。隔离**不等于**业务确认完成：连续确认位置（AckPosition）与消费位置（Position）都会停在隔离消息形成的空洞之前，绝不越过它把后续确认误当成前缀完成；只有“可继续投递后续消息”的位置（DeliverPosition）会越过隔离点。可用 Quarantined 单独核对，AckedBy 中不会出现它。
- Redeliver 人工重投被隔离消息：保留原消息身份（主题/偏移/内容），清除失败计数，下一次 Pull 以新纪元投递；尝试序号不重置，而是在历史之上继续累计（跨超时、重启均连续），操作者记入历史。
- Abandon 人工明确放弃被隔离消息：写入 abandon 历史事件（含操作者与事由）后永不投递。消费位置（Position）依据该放弃事件越过它并推进，但连续确认位置（AckPosition）仍停住——放弃与确认严格区分。可用 Abandoned 核对。
- 三种位置分开表示，回答不同问题：Position = 连续已处理（已确认或已放弃）前缀；AckPosition = 连续已确认前缀（隔离/放弃都不算）；DeliverPosition = 已确认/已放弃/已隔离的连续前缀，即“后续消息能否继续投递”。
- Progress 一次给出 Total / Delivered / Acked / Quarantined / Abandoned / Pending 与三个位置，且 Acked+Quarantined+Abandoned+Pending == Total，可在重启后分别核对已交付、已确认、隔离与仍待处理的数量。
- 每一次领取、超时、拒绝、确认、隔离、人工重投、人工放弃都留在消息历史（History）里；最终确认者（AckedBy）不代替全部尝试记录。
- 旧领取令牌迟到、重启后再次投递、重投后处理失败都不会重复确认：纪元 fencing 拒绝旧令牌（ErrStaleToken），已确认消息的迟到令牌返回 ErrAlreadyAcked，全量确认去向（AckRecords）始终每消息至多一条。
- 重启后可用 Progress / AckedBy / History / Quarantined / Abandoned 核对每条消息的实际去向与全部尝试。
